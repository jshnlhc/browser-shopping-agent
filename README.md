# Browser-Level Shopping Agent for Chinese E-Commerce

**面向中文电商平台的浏览器级购物智能体**

一套基于 **有头浏览器 + Chrome DevTools Protocol (CDP)** 的电商自动化工具链与实证方法论。

> ⚠️ **这不是抢购脚本，也不是刷单工具。**
> 本项目不破解加密、不伪造身份、不绕过实名与支付校验，只以真实浏览器完成**用户本人授权范围内**的购物操作。设计目标是"把付款界面安全地交到用户手上"，而不是"替用户完成支付"。

---

## 为什么不用无头浏览器？

这是本项目最重要的结论，来自对京东与淘宝的实测对照：

| 维度 | 无头 + 指纹伪装 | 有头 + 真实指纹 |
|---|---|---|
| 淘宝搜索页 | 商品区「加载中」，页面文本 838 字符 | 正常渲染，7672 字符 |
| 京东登录态 | **UA 伪装后失效且不可恢复**（302 → passport.jd.com） | 稳定 |
| 浏览器指纹一致性 | 需持续对抗数十个关联维度 | 天然一致，零维护 |
| 变更适应性 | 检测更新即失效 | 随真实用户同步演进 |

根因：**反自动化检测的核心维度是「一致性」**。无头方案必须同时伪造数十个相互关联的指纹维度，任何一处不一致都会暴露；有头方案以真实浏览器为载体，一致性是免费的。

更反直觉的是 **UA 伪装对两个平台方向相反**：伪装成正常 Edge UA 能修复淘宝的渲染问题，却会摧毁京东的登录态（京东将凭证与设备指纹绑定）。

## 快速开始

### 1. 启动独立浏览器实例

```bash
msedge.exe \
  --remote-debugging-port=9335 \
  --user-data-dir=/path/to/your/shopping-profile \
  --disable-blink-features=AutomationControlled
```

保持**有头模式**（不要加 `--headless`），也**不要传 `--user-agent`** —— 有头模式的 UA 天然干净，可同时满足淘宝与京东。

### 2. 由你本人在该窗口中登录

登录态保存在这个独立 profile 里（浏览器原生加密存储）。本项目**不读取、不导出、不持久化任何 cookie 或 token**。

### 3. 使用脚本

```bash
# 硬登录验证（推荐先跑这个）
node scripts/shop-login-probe.mjs 9335

# 打开页面并导出渲染后的文本
node scripts/shop-grab.mjs "https://cart.jd.com/cart_index" out.txt 9335 13000 2

# 在页面上分步执行任意 JS（交互、读状态）
node scripts/shop-eval.mjs "https://cart.jd.com/cart_index" 9335 13000 step1.js step2.js

# 截图
node scripts/shop-shot.mjs 9335 shot.png "cart_index"

# 捕获 XHR / 接口响应体
node scripts/shop-net.mjs "https://item.jd.com/100159918316.html" out.json 9335 15000
```

无需任何第三方依赖 —— 需要 Node.js ≥ 26（使用内置的全局 `WebSocket`）。

## 核心方法论：状态判据的权威层级

同一事实往往存在多个可观测来源，**必须建立权威层级，不能混用**。这是本项目最实用的产出：

| 判据对象 | ✅ 权威来源 | ❌ 不可信来源 |
|---|---|---|
| 登录态 | 受保护页重定向测试 | cookie 存在性（京东掉线后 cookie 仍在！） |
| 购物车数量 | 新开页面的「商品总额」（原价 × 件数） | 页面内未刷新的到手价 |
| 订单价格 | 结算页的分摊实付 | 商品页「到手价」标签 |
| 运费 | 结算页是否存在「运费」金额行 | 依据"满 X 元包邮"规则推断 |
| 写操作是否生效 | 重新加载后的服务端状态 | 接口的返回码（可能静默失效） |

**六条判据速记**：

- **P1** 登录态 = 受保护页重定向测试
- **P2** 写操作 = 重新加载后的服务端状态
- **P3** 数量 = 商品总额 ÷ 原价单价
- **P4** 价格 = 结算页分摊实付
- **P5** 运费 = 结算页金额行是否存在
- **P6** 兼容性 = 厂商显式标注 + 官网参数

## 实测到的风控阈值（重要）

本项目用一次**有代价的实验**测出了京东的频率型风控阈值 —— 代价是消耗了该账号的宽容度预算（此后采集被迫转为离线解析）：

| 指标 | 实测值 |
|---|---|
| 触发端点 | 商品**详情页**（`item.jd.com`），降级 URL 携带 `from=pc_item&reason=403` |
| 临界强度 | **≈ 2.2 次导航/分钟**（11 次导航 / 304 秒） |
| 降级形态 | 重定向至频控页，文本从 4,000–5,100 字符降至 **824**（**−82%**） |
| 恢复时间 | **≈ 24 分钟**，且恢复是**渐进**的 |
| 二次触发 | 恢复后立即以 1/3 强度采样，**首次访问即被再次降级**，并升级为「人机验证」 |

**三条可操作结论**：

1. **风控按端点分级，不是账号级一刀切。** 同一账号在**搜索结果页**上以相近强度（2.4 次/分钟）连续采样 54 次未触发频控，而在**商品详情页**上 5 分钟即触发。采样策略必须按端点分别设限。
2. **恢复期的探测是负收益的。** 触发后以 2–4 分钟间隔持续探测，8 分钟内未见恢复；停止探测 16 分钟后自行恢复。探测既取不到数据，又推迟恢复。
3. **「页面恢复正常」≠ 完全恢复。** 宽容度是渐进回升的，刚恢复时的安全强度远低于初始值。

**工程建议**：详情页访问控制在 **< 0.5 次/分钟**，并对所有导航做端点级计数；一旦触发频控，**停机 ≥ 30 分钟**，不要重试试探。

## 平台基线与数据质量（9 平台 × 3 关键词 × 2 重复 = 54 次观测）

| 平台 | 领域 | 文本长度 (mean ± sd) | 请求数 | 商品命中 |
|---|---|---|---|---|
| 淘宝 | 电商 | 6,727 ± 595 | 348 | 33.5 |
| 京东 | 电商 | 5,230 ± 168 | 238 | 16.2 |
| 抖音 | 内容 | 4,371 ± 504 | **449** | 1.2 |
| B站 | 内容 | 2,936 ± 175 | 144 | 2.0 |
| 苏宁易购 | 电商 | 2,900 ± 433 | 150 | **0** |
| 拼多多 | 电商 | 1,871 ± 79 | 116 | 22.5 |
| 唯品会 | 电商 | 842 ± 0 | 145 | **0** |
| 知乎 | 内容 | 804 ± 0 | 162 | **0** |
| 美团 | 本地生活 | — | — | **无 PC 商品入口** |

**有效数据率仅 85.2%**（46 VALID / 2 DEGRADED / 6 INVALID_LOW）—— **不做质量门控就直接取均值，会得到虚假的平台差异。**

两条容易被忽略的结论：

- **文本量 ≠ 商品可得性。** 拼多多的文本量只有淘宝的 28%，商品命中数却与之相当（22.5 vs 33.5）；苏宁与唯品会渲染出 842–2,900 字符，商品命中为 **0**（返回的是分类页）。故「渲染完整度」不能作为「任务可用性」的代理指标。
- **降级分查询级与账号级两层。** 京东「数据线」关键词在正常批次中出现 1,048 字符（−79%）且商品命中归零，而同批次其他关键词正常 —— 这是**查询级**降级，换关键词即可；`reason=403` 则是**账号级**，必须停机冷却。二者的诊断线索与修复策略完全不同。

## 中文商品页的字段结构（三层，不是一张表）

抓取商品属性时，**不要**把整页当成一个属性集合 —— 京东详情页的字段分布在三个语义角色完全不同的区域：

| 区域 | 内容 | 语义角色 | 覆盖率（6 商品实测） |
|---|---|---|---|
| **A 规格参数表** | 键值对（紧随最后一个「商品详情」之后） | 产品固有属性 | 通用字段仅 **3/39（7.7%）**：包装清单、品牌、商品编号 |
| **B 销售变体** | 多行选项列表 | 交易选项（买哪一件） | 颜色 6/6、系列品 5/6、版本 3/6 |
| **C 服务承诺** | 「·」分隔的承诺串 | 履约承诺（交易是否可行） | **6/6（100%）** |

**关键点**：A 区覆盖全部样本的 3 个字段**没有一个是描述产品本身的** —— 产品描述性字段（材质、尺寸、容量、功率、防水等级）**全部是品类特化的**。这意味着**跨商品的属性级比较在中文平台上缺乏可靠的数据基础**，智能体实际只能退回标题文本与**评价标签**（如「贴合度很高 399」，是众包维度而非平台声明）。

C 区（履约承诺）以 100% 的覆盖率与产品规格**并列**呈现，是中文商品页的一个显著结构特征 —— 它是「不支持 7 天无理由退货」这类硬约束的**可程序化提取**来源。

## 人机边界（禁令清单）

智能体在以下环节**必须停手**，并执行交接协议（恢复浏览器窗口 → 置前台 → 说明所需的人类操作）：

1. 不填写任何实名信息（姓名、证件号、银行卡号）
2. 不索取、不代填短信验证码
3. 不输入支付密码
4. 不点击「立即支付」或任何等价的订单提交动作
5. 不读取、不导出、不持久化任何 cookie 或 token
6. 不在风控敏感页面（结算页、支付页）进行高频操作

> 第 6 条来自一次真实教训：为核对运费而连续四次打开结算页，触发了平台的风控升级，此后每次访问结算页都被强制重定向至实名认证页。**观测行为本身会改变被观测系统。**

## 适用范围与免责

**适用**：个人用户在自己账号、自己设备上，以真实浏览器完成自身授权的购物流程。

**不适用**：抢购、刷单、养号、薅羊毛、批量下单，以及任何违反平台用户协议的行为。本项目不提供任何绕过平台风控、实名认证或支付校验的手段 —— 这些边界在技术与法律上均不可规避。

**时效性提醒**：文中所有 DOM 结构、接口行为、价格规则均记录于 2026 年 9 月，具有强时效性，平台迭代后可能失效。本项目的主张恰恰是：**这个领域不存在"一次编写永久可用"的脚本，只有"能看见、能重抓"的方法论。**
