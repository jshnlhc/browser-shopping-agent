# 面向中文电商平台的浏览器级购物智能体：凭证安全、反自动化对抗与人机边界

**Browser-Level Shopping Agents for Chinese E-Commerce: Credential Safety, Anti-Automation Dynamics, and Human–Agent Boundaries**

*—— 一份基于真实平台的实证经验报告*

---

## 摘要

基于大语言模型的 Web/GUI 智能体在沙箱基准上进展迅速，但在真实中文电商平台上的可行性缺乏公开的实证研究。本文报告一套以**有头浏览器 + Chrome DevTools Protocol (CDP)** 为核心的购物智能体方法，并在京东、淘宝/天猫、拼多多、抖音商城、苏宁、1688、得物七个真实平台上进行了系统性实测。我们的核心主张是：**在强风控的中文电商环境中，智能体的瓶颈不在推理能力，而在"载体真实性"与"状态判据的可靠性"**。

本文的贡献包括：（1）提出三层架构（浏览器载体 / CDP 控制面 / 领域逻辑）与凭证安全约束 —— 登录由用户在独立浏览器 profile 内完成，凭证不落盘、不过手，规避了现有开源方案普遍存在的明文 cookie 泄露风险；（2）发现并记录了一组**反直觉的失效模式**，包括用户代理（UA）伪装对淘宝与京东的**反向效应**（伪装 UA 修复淘宝渲染却摧毁京东登录态）、改数量接口"返回成功但静默失效"、以及数量控件中**减号与加号共用同一 CSS Modules 类名**的结构陷阱；（3）针对电商场景提出**状态判据的权威层级**（受保护页重定向测试 > 结算页实付 > 商品页标价），并给出"到手价"与结算价之间差异的机制解释；（4）明确划定了**不可自动化边界**（实名认证、支付、短信验证码），并论证其不可规避性。我们同时开源了工具链与流程规范。

**关键词**：Web 智能体；浏览器自动化；Chrome DevTools Protocol；电商；反自动化检测；人机协作

## 1 引言

大语言模型驱动的图形界面智能体（GUI Agent）已成为自动化人机交互的主流范式[^1][^2]。在 Web 场景中，研究界构建了 Mind2Web[^3]、WebArena[^4]、WebVoyager[^5] 等基准，推动智能体的网页导航能力快速提升。

然而，Xue 等人[^6]在 COLM 2025 的工作给出了一个警示性的结论：前沿 Web 智能体在更贴近真实使用场景的 Online-Mind2Web 基准（300 个任务、136 个真实网站）上，成功率相比 WebVoyager 上的报告值**大幅下降**，此前结果存在系统性过度乐观。这一"进步幻觉"提示我们：**沙箱环境与真实生产网站之间存在结构性鸿沟**。

中文电商平台是这一鸿沟的极端案例。与英文沙箱站点相比，它们具有三个显著特征：

1. **强风控**：登录凭证与设备指纹深度耦合，行为序列被持续建模；
2. **强动态性**：前端技术栈频繁迭代，接口与 DOM 结构无兼容承诺；
3. **强监管**：支付环节受实名制约束，存在法律意义上的不可自动化边界。

现有电商智能体研究多集中于**模拟环境**（如 WebShop[^7] 的 118 万商品模拟站）或**决策层面**（如 ACES 框架[^8] 对智能体选品偏好的审计），而"如何在真实中文电商平台上把一次购买流程真正跑通"这一工程问题，公开文献中缺乏系统记录。

本文以一次真实的跨平台比价与加购任务为载体，报告我们的方法、实测数据与失效分析。我们刻意采用**经验报告（experience report）**体裁：不追求统计显著性，而追求**失效模式的完整记录与机制解释**，因为在这个领域，恰恰是那些一手的、反直觉的失败教训最具复用价值。

**本文贡献**：

- **C1** 一套凭证安全的浏览器级智能体架构，与现有开源方案的明文凭证做法形成对照（§4）；
- **C2** 七个平台的实测覆盖矩阵与五类关键失效的机制分析（§6）；
- **C3** 电商场景下"状态判据权威层级"的形式化，及"到手价 ≠ 结算价"的机制解释（§4.5、§6.4）；
- **C4** 不可自动化边界的明确划定与伦理论证（§4.6、§7.3）。

## 2 相关工作

### 2.1 Web 与 GUI 智能体

Mind2Web[^3] 首次大规模构建了跨网站的通用网页智能体数据集；WebArena[^4] 提供了可复现的自托管沙箱环境；WebVoyager[^5] 转向真实在线网站评估；OSWorld[^9] 与 AndroidWorld[^10] 将范围扩展到操作系统与移动端。

综述工作方面，Nguyen 等人[^1] 系统梳理了 GUI 智能体的感知—规划—执行框架；Shi 等人[^2] 从可信视角提出 **"执行间隙"（execution gap）** 概念，即感知、推理与交互在动态、部分可观测界面中的错位，并系统评述了各阶段的失效模式与对抗攻击。本文将"执行间隙"具体化到电商场景，给出五类真实失效的实例。

### 2.2 基准可靠性与真实环境评估

Xue 等人[^6] 的 Online-Mind2Web 是本文最重要的方法论参照：他们不仅提出了更严格的基准，还揭示出 **WebVoyager 的任务偏易、可被 Google 搜索等捷径解决**。这直接支持了本文的立场 —— 在真实电商网站上，任何"捷径"都会被风控体系封堵，智能体必须真正完成浏览器级交互。

### 2.3 电商智能体

WebShop[^7] 提供了 118 万真实商品、12,087 条众包指令的模拟环境，是电商智能体的奠基性工作。近期工作转向更复杂的设定：ShopSimulator[^11] 探索面向购物助手的强化学习驱动智能体；ProductResearch[^12] 通过多智能体合成轨迹蒸馏训练电商深度研究智能体；另有工作构建了面向长时程、偏好锚定的电商任务基准[^13]。

Allouah 等人[^8] 的 ACES 框架从经济学视角审计智能体决策，发现**选择同质化（choice homogeneity）**、**位置偏见（position bias）**以及对赞助标签的惩罚等系统性偏差，且这些偏好随模型版本更新剧烈波动。该工作分析的是智能体的**决策层**；本文关注其**执行层** —— 两者互补。

值得注意的是，京东云开发者社区公开的技术分享讨论了电商垂域多智能体落地中"准确率低、幻觉、场景区分度差"的问题[^14]，侧面印证了真实平台的工程难度。

### 2.4 反自动化检测与规避

浏览器指纹与自动化检测的对抗是一个长期存在的攻防领域。工业界的公开分析[^15] 系统总结了基于 JavaScript 的检测、指纹检测等手段及对应的规避策略（如 stealth 插件、定制化浏览器构建）。Browseless 的 2026 年技术指南[^16] 进一步指出，**指纹与配置的一致性**（fingerprint and profile consistency）是检测的核心维度。

一个关键的时效性证据是：Chrome 官方于 2025 年发布了 [DevTools MCP 服务器](https://developer.chrome.com/blog/chrome-devtools-mcp?hl=zh-cn)[^17]，将 CDP 能力以 Model Context Protocol 形式暴露给 AI 智能体。这表明**基于真实浏览器调试协议的智能体控制**已成为工业界认可的方向，本文的方法正是在这一路线上的一次独立实践与验证。

## 3 问题设定与挑战

### 3.1 任务定义

我们考虑如下任务：给定一个自然语言购物需求 $q$（例如"为某款手机买一片钢化膜"），智能体需在多个电商平台 $P = \{p_1, \dots, p_n\}$ 上完成：

1. **检索**：找到候选商品集 $\{g_i\}$；
2. **验证**：进入商品详情页，获取真实参数与价格；
3. **比价**：在**同口径**下比较候选（考虑运费、优惠、配送可达性）；
4. **决策**：依据用户硬约束（如兼容性）筛选；
5. **执行**：加入购物车、调整数量与勾选状态；
6. **交接**：将付款界面移交给人类用户。

约束条件：**支付及任何涉及金融凭证的操作不得由智能体完成**。

### 3.2 四类挑战

**C1 — 登录态与设备指纹的耦合。** 中文电商平台普遍将登录凭证与浏览器指纹绑定。这导致一个反直觉的后果：任何用于"改善抓取"的指纹修改，都可能使已建立的登录会话失效。

**C2 — 反爬与风控的分层。** 平台的风控同时在多个层面生效：传输层（UA、TLS 指纹）、渲染层（懒加载、虚拟列表、Canvas 干扰）、交互层（行为时序、鼠标轨迹）、业务层（频率限流、异常访问判定）。单点规避无效。

**C3 — 凭证安全约束。** 用户必须登录才能访问购物车与结算流程，但把凭证交给第三方程序是重大安全风险。现有开源方案普遍将 cookie 持久化为明文 JSON 文件（§6.3.6 记录了一起真实泄露案例）。

**C4 — 不可自动化边界。** 实名认证、短信验证码、支付密码、人脸识别等环节，构成了法律与安全上的硬边界，智能体必须在此处停手。

## 4 方法

### 4.1 总体架构

我们采用三层架构：

| 层 | 职责 | 实现 |
|---|---|---|
| **载体层** | 提供真实的浏览器运行时与登录态 | 有头 Edge，独立 user-data-dir |
| **控制层** | 感知与动作的统一接口 | Chrome DevTools Protocol over WebSocket |
| **领域层** | 电商语义（比价、加购、判据） | 平台特定的脚本与规则 |

**核心设计原则：让载体尽可能接近真实用户，把复杂性交给真实浏览器，只在必要时才退回解析 DOM 或接口。** 这与主流方案（无头浏览器 + 指纹伪造）形成鲜明对比，其依据见 §7.1。

### 4.2 登录态管理（应对 C1、C3）

**M1.1 独立 profile 隔离。** 使用专用 `--user-data-dir` 启动浏览器实例，配合 `--remote-debugging-port` 暴露 CDP。登录态由用户在该实例内**手动完成**（扫码或密码），智能体全程不接触凭证。

**M1.2 凭证不落盘原则。** 智能体不读取、不导出、不持久化任何 cookie 或 token。现代浏览器（Edge/Chrome 127+）已全面采用 App-Bound Encryption（v20）保护 cookie，其实钥绑定调用进程身份，这使得"复制 profile 复用登录态"在技术上亦不可行 —— 客观上强化了这一原则。

**M1.3 登录判据的修正。** 这是一个关键的实证发现：**cookie 的存在与否不能作为登录判据**。我们观察到，京东会话失效后，cookie 存储中仍保留 `pin` 与 `thor` 字段，基于 cookie 的检测脚本报告"已登录"，而实际业务页面全部 302 重定向至 `passport.jd.com`。

> **判据 P1（登录权威测试）**：访问一个受保护页面，观察其最终落地 URL 是否被重定向至登录页。这是唯一可靠的登录判据。

### 4.3 感知层（应对 C2）

**M2.1 视口放大以对抗懒加载。** 通过 `Emulation.setDeviceMetricsOverride` 将视口高度放大至常规值的 3–4 倍（如 1512×2600），配合重复的 `window.scrollTo(0, document.body.scrollHeight)`。实测表明，**视口放大是虚拟列表与懒加载最有效的触发手段**，优于滚动事件注入。

**M2.2 分级感知策略。** 按可靠性递减顺序：

1. **DOM 直读**（`Runtime.evaluate` 取渲染后的文本与结构）—— 首选；
2. **接口响应捕获**（`Network.enable` + `loadingFinished` 时立即 `getResponseBody`）—— 对结构化数据有效，但面对加密响应失效（见 §6.3.4）；
3. **视觉与坐标交互** —— 当前两者均失效时的最后手段。

### 4.4 动作层

**M3.1 真实事件序列。** 现代前端框架（React 等）依赖完整的合成事件链。实测发现，仅派发 `click` 往往不足以触发受控组件的行为，需要完整的序列：

```
pointerdown → mousedown → pointerup → mouseup → click
```

并携带有效的 `clientX/clientY`（取自元素 `getBoundingClientRect` 的中心）。

**M3.2 坐标级点击。** 当页面无可用 DOM 选择器时，回退到 CDP `Input.dispatchMouseEvent` 在真实坐标处点击。这是突破拼多多（其商品列表零 `<a>` 标签、`goods_id` 不存在于 HTML、XHR 响应体加密为 `{"rc-res-data": "..."}`）的唯一有效手段。

### 4.5 状态判据的权威层级

本文提出一个对电商智能体至关重要的方法论：**同一事实存在多个可观测来源时，必须建立权威层级，不能混用。**

| 判据对象 | 权威来源 | 不可信来源 |
|---|---|---|
| 登录态 | 受保护页重定向测试 | cookie 存在性 |
| 购物车数量 | 新开页面的「商品总额」（原价 × 件数） | 页面内未刷新的到手价显示 |
| 订单价格 | 结算页的分摊实付 | 商品页「到手价」标签 |
| 运费 | 结算页中是否存在「运费」金额行 | 依据"满 X 元包邮"规则推断 |
| 接口操作是否生效 | 重新加载后的服务端状态 | 接口的返回码 |

其中「接口返回成功但静默失效」值得特别强调（判据 P2）：

> **判据 P2（写操作验证）**：任何改变服务端状态的接口调用，其成功与否**必须通过重新加载页面来验证**，接口自身的返回体不构成证据。

### 4.6 人机边界协议（应对 C4）

我们明文划定智能体的**禁令清单**：不填写任何实名信息；不索取、不代填短信验证码；不输入支付密码；不点击"立即支付"及等价的提交订单动作。

当流程触及边界时，智能体执行**交接协议**：①停止推进；②将浏览器窗口从隐藏状态恢复并置于前台（`ShowWindow(hwnd, 9)` + `SetForegroundWindow`）；③以自然语言说明当前状态与所需的人类操作。

这一设计不仅是安全要求，也是**风险控制**：测试表明，在风控敏感的页面上频繁操作会提升校验级别（§6.3.5）。

## 5 实现

工具链以 Node.js（≥ 26，使用内置全局 `WebSocket`，无需第三方依赖）与 PowerShell 实现，核心组件如下：

| 组件 | 功能 |
|---|---|
| `shop-grab.mjs` | 页面渲染 → 视口放大 → 滚动 → 文本导出 |
| `shop-eval.mjs` | 在目标页面分步执行任意 JavaScript（交互与状态读取） |
| `shop-shot.mjs` | 页面截图（`Page.captureScreenshot`） |
| `shop-login-check.mjs` | cookie 快检（**仅作参考，依 P1 不得单独采信**） |
| `shop-login-probe.mjs` | 硬登录验证（P1 的实现） |
| `shop-net.mjs` | XHR/接口响应体捕获 |

窗口管理通过 user32 API（`ShowWindow` / `SetForegroundWindow` / `IsWindowVisible`）实现"有头运行、无头体验"：日常操作时窗口隐藏（SW_HIDE = 0），需要人类介入时恢复（SW_RESTORE = 9）。

## 6 案例研究

### 6.1 任务与设置

**任务**：为两台手机（机型 A，6.83 英寸，3D 超声波指纹；机型 B，6.67 英寸 2K 直屏，超声波指纹）各购买一片钢化膜，收货地址位于中国西北偏远地区。

**环境**：Windows 11；Edge 153（有头模式）；独立 profile；CDP 端口 9335；UA 为自然的有头 UA（`Chrome/153.0.0.0 Safari/537.36 Edg/153.0.0.0`）。

### 6.2 平台接入能力验证

我们将"接入"定义为三个可**独立验证**的维度，只有三者同时成立才算通过：

- **可达性（Reachability）**：目标页面正常渲染，而非空壳、跳转或风控验证页。判据为渲染后的文本长度与页面标题。
- **登录态（Session）**：能观察到用户自身的会话痕迹（导航栏中的账号、投稿或订单入口等），而非游客视图。
- **数据提取（Extraction）**：能从渲染结果中解析出**结构化语义元素**（价格、商品标题、话题标签、作者等），且数量级符合真实内容而非占位结构。

按此标准逐平台实测，结果如下：

| 平台 / 业务线 | 可达性 | 登录态 | 数据提取 | 结论 |
|---|---|---|---|---|
| 京东 | ✅ | ✅ | ✅ 商品、价格、购物车、结算页 | **通过** |
| 淘宝 / 天猫 | ✅ | ✅ | ✅ 商品列表与详情页 | **通过**（须注意 §6.3.1） |
| 拼多多 | ✅ | ✅ | ✅ 商品详情 | **通过**（需坐标级交互，§6.3.4） |
| 抖音（内容搜索） | ✅ | ✅ | ✅ 7,486 字符 / 244 个话题标签 / 87 个作者 | **通过** |
| 闲鱼 | ✅ | ✅ | — | 登录态通过，数据提取未测 |
| 苏宁易购 | ✅ | — | ❌ | 未通过：目标品类无货 |
| 1688 | ⚠️ | ❌ | ❌ | 未通过：返回不相关结果，且需登录 |
| 得物 | ❌ | — | — | 未通过：网页端仅有 App 下载引导 |
| 美团（到店业务） | ❌ | — | — | 未通过：PC 端仅有企业官网，到店业务 H5 入口不对公网开放 |
| 抖音商城（团购 / 本地生活） | ❌ | — | — | 未通过：搜索仅有综合/视频/用户/直播四类，无团购类目 |

**关于抖音的一个关键区分**：同一域名下，**内容搜索接入通过，而团购（本地生活）接入不通过**。`https://www.douyin.com/search/{keyword}` 能正常返回内容结果，并可解析出话题标签与作者；但搜索结果页的类目仅有「综合 / 视频 / 用户 / 直播」，不存在团购类目，`www.douyin.com/life` 会重定向回精选页，`life.douyin.com` 无法建立连接。观察到的「抖音团购」「团购套餐」字样均属搜索**联想词**，而非可用的筛选入口。

这一点值得单独强调：**联想词的存在会诱导智能体误判功能存在** —— 在自动化流程中，若把联想词当作可点击的类目入口，将得到"点击无反应"的静默失败，而失败原因并非网络或权限，而是该功能在此端根本不存在。识别方法是**核对点击前后的页面结构变化**，而非以元素文本是否出现为准。

**发现**：在十个被考察的平台/业务线中，**仅四个通过完整接入验证**。这一覆盖率远低于文献中通常假设的场景，说明真实电商智能体的"可用域"远比想象中狭窄。进一步地，接入失败的原因可分为三类，其可修复性截然不同：

1. **业务不在 Web 端**（得物、美团到店）—— 结构性问题，不可通过技术手段修复；
2. **风控拦截**（1688 需登录；美团 H5 曾出现 `verify.meituan.com` 的 `spiderindefence` 重定向）—— 需人类介入或降低操作频率；
3. **功能本身不存在**（抖音团购类目）—— 不可修复，且最易被联想词误导。

区分这三类的意义在于：只有第 2 类值得投入工程成本，而第 1、3 类应当尽快终止尝试，把时间留给可用路径。

### 6.3 五类关键失效与修复

#### 6.3.1 UA 伪装的反向效应

这是本文最具反直觉性的发现。我们最初观察到淘宝搜索页商品区域长期显示「加载中」，页面文本仅 838 字符；根因是**无头 UA 特征**（UA 中含 `HeadlessChrome`）。覆盖为正常 Edge UA 后：

- **淘宝**：页面文本从 **838 字符恢复至 7672 字符**，商品正常渲染 ✅
- **京东**：**登录态被摧毁** —— `item.jd.com` 与 `cart.jd.com` 均 302 至 `passport.jd.com/new/login.aspx?...czLogin=1`，且切回有头模式、移动窗口位置均无法恢复，只能由用户重新扫码 ❌

**机制解释**：京东将凭证与设备指纹（含 UA）绑定，UA 变更被判定为设备变更，触发会话失效。这意味着**两个平台的伪装需求相互冲突，无法在同一 profile 上同时满足**。

**修复**：放弃 UA 伪装，改用**有头模式 + 不覆盖 UA**。有头模式的 UA 天然干净，可同时满足两个平台。

#### 6.3.2 登录判据的失效（→ 判据 P1）

如上所述，京东会话失效期间，cookie 快检脚本仍报告"已登录（50 条 cookie，含 pin）"。该失效直接催生了判据 P1。

#### 6.3.3 改数量接口的静默失效（→ 判据 P2）

京东购物车的传统接口 `cart.jd.com/changeNum.action?pid=&pcount=` 返回：

```json
{"isLogin":1,"pcount":1,...}
```

形态上完全正常，但**新版 SPA 购物车不接受该接口的影响** —— 重新加载后数量不变。这印证了判据 P2 的必要性。

**有效替代**：直接点击页面上的数量控件。

#### 6.3.4 数量控件的结构陷阱

新版购物车使用 CSS Modules 哈希类名。我们发现一个极易误判的结构：

```html
<!-- 减号 -->
<button class="_flex-plus-container_1ep1a_41">
  <div class="_flex-plus_1ep1a_41">
    <div class="_flex-plus-horizontal_1ep1a_46"></div>
  </div>
</button>
<!-- 加号：类名完全相同，仅多一条竖线 -->
<button class="_flex-plus-container_1ep1a_41">
  <div class="_flex-plus_1ep1a_41">
    <div class="_flex-plus-horizontal_1ep1a_46"></div>
    <div class="_flex-plus-vertical_..."></div>
  </div>
</button>
```

**减号与加号共用同一类名 `_flex-plus-container`**，按语义搜索 `minus` 必然返回空集。唯一可靠的识别方式是**解析内部图标结构**：仅含 `horizontal`（一条横线）者为减号。此外，当数量为 1 时，减号元素会附加 `_is-disabled_*` 类。

#### 6.3.5 实名认证墙与风控升级

在核对运费的过程中，我们先后四次访问结算页，并在看到「完善实名信息」引导弹窗后点击了"下次再说"。此后，**每次访问结算页均被强制重定向**至 `authpay.jd.com` 的实名认证页，要求填写银行卡号、银行预留手机号并接收短信验证码。

**分析**：①该页面为支付前置校验，属账号级要求，非设备级 —— 换设备（如手机）无法规避；②高频访问结算页与关闭引导弹窗**很可能是触发风控升级的直接原因**。

**方法论启示**：对风控敏感页面，**核价应当一次到位**（单次抓取即读取运费、商品总额、优惠与实付），避免反复导航。这是"观测行为本身改变被观测系统"的一个典型案例。

#### 6.3.6 开源方案的凭证安全对照

作为对照，我们审计了两个相关开源项目：

- **`frieren-123/shopping-agent-ai`**（LLM 跨平台比价，含京东/淘宝/唯品会爬虫）：设计上有可借鉴之处（商品打分、参数提取、报告生成），但**作者将本人 2 MB 的淘宝完整 cookie、以及小红书、知乎 cookie 一并提交至公开仓库**。此外其技术路线为无头 Playwright，与我们 §6.3.1 的实测结论相悖。
- **`hamibot/hamibot`**（安卓 JavaScript 自动化，★3116）：**无需 root**，基于无障碍服务（`com.stardust.automator` 封装 UI 树与 BFS/DFS 选择器）。技术上是移动端最现实的路径，但①无障碍服务是电商 App 的重点风控特征；②其脚本市场内容以"刷金币/养号/刷单"为主，与平台规则高度冲突。

**结论**：本项目采纳的"用户自主登录 + 凭证不落盘 + 有头浏览器"路线，在上述对照组中具有明确的安全优势。

### 6.4 价格的真实性：到手价 ≠ 结算价

京东商品页对"预估到手价"的定义为：

> 预估到手价 = 商品标价 − 优惠券 − 满减（或折扣）− 新客优惠……

并明确说明：**"购买多件商品而满减活动仅支持享受 1 次"**。

我们实测到这一规则的具体后果：

| 口径 | 金额 |
|---|---|
| 两件商品标签价之和 | ¥20.60 |
| 结算页实际合计 | ¥27.10 |
| **差额** | **¥6.50** |

其中结算页给出的分摊实付为：机型 A 膜 ¥14.39 + 机型 B 膜 ¥12.71；商品总额 ¥42.00，共减 ¥14.90。

**推论**：①"分开下单更省"这一直觉在满减规则下**不成立**（分单后满减仍只享 1 次，且增加运费风险）；②任何基于标签价的比价都不可靠，**必须落到结算页口径**。

**运费判据**：京东自营基础运费 6 元、订单实付满 59 元免运费。本单 ¥27.10 不满足门槛，但结算页中**不存在任何运费金额行**（全文唯一匹配"运费"的是页脚帮助链接）。据此判定免运费 —— 这与"按规则推断应收 6 元"相反，再次说明**判据应取自权威来源而非规则演绎**。

### 6.5 选品决策中的硬约束

本任务的选品受一条硬约束支配：**3D 超声波指纹屏对贴膜的厚度与材质敏感**。

- vivo 官方支持文档指出，超声波指纹机型使用非官方钢化膜可能导致传感器信号变弱[^18]；
- 荣耀官方文档进一步说明"保护膜的材质和厚度会影响超声波的发射与反射"，并给出操作建议：**贴完后删除全部指纹并重新录入**[^19]；
- 业界建议超声波特性的膜厚区间为 0.15–0.2 mm。

最终选定的两款绿联（UGREEN）京东自营膜，其官方参数均为「电镀 + 全胶」工艺；其中机型 B 款在标题中明确标注**「超声波秒解锁」**，而机型 A 款官方参数为 **0.25 mm** 且**未标注超声波兼容** —— 后者构成风险点，须通过"贴前录指纹、贴后重录 + 开启触控灵敏度"的操作流程来缓解。

**方法论意义**：兼容性约束的判据应取自**厂商显式声明**（标题/规格中的适配标注）与**官网参数页**，而非"全胶/边胶"这类粗粒度的工艺分类。

## 7 讨论

### 7.1 为什么有头优于无头

主流自动化方案倾向无头浏览器 + 指纹伪造。本文的实测数据支持相反的结论：

| 维度 | 无头 + 伪装 | 有头 + 真实指纹 |
|---|---|---|
| 淘宝搜索页 | 「加载中」，838 字符 | 正常，7672 字符 |
| 京东登录态 | 伪装后失效且不可恢复 | 稳定 |
| 浏览器指纹一致性 | 需持续维护对抗检测 | 天然一致 |
| 维护成本 | 检测更新即失效 | 与真实用户同步演进 |

更深层的原因与 §2.4 的工业分析[^15][^16] 一致：检测的核心维度是**一致性**。无头方案必须同时伪造数十个相互关联的指纹维度，任何一处不一致都会暴露；而有头方案以真实浏览器为载体，**一致性是免费的**。

### 7.2 脆弱性与可维护性

本文的方法并不"鲁棒"—— 它在一日内即遭遇两次前端变更（接口静默失效、类名结构陷阱）。我们主张：**在该领域，"一次编写永久可用"是不可能的幻象，正确的目标不是鲁棒而是可观测与可修复**。

具体而言，智能体应具备：①随时重新感知的能力（不依赖缓存的选择器）；②判据的权威层级意识（知道该信谁）；③把"未知"而非"猜测"作为默认输出。

### 7.3 伦理、合规与责任边界

**合规性**：本方法不破解加密、不伪造身份、不绕过实名与支付校验，仅以真实浏览器完成用户本人授权范围内的操作。这与"抢购脚本""刷单工具"存在本质区别。

**风险提示**：我们不建议将本方法用于违反平台用户协议的高频操作（抢购、刷单、养号）。文献[^8] 关于智能体市场的波动性分析表明，自动化行为会引发平台侧的持续对抗，最终损害所有用户。

**责任边界**：智能体必须可解释地停手于金融环节。本文的交接协议（§4.6）是一个具体实现。

### 7.4 局限

1. **样本规模**：本文基于单次任务的深度案例研究，不构成统计意义上的评估。观察结论的普适性有待多任务验证。
2. **平台时效性**：所述 DOM 结构、接口行为、价格规则均具有强时效性（记录于 2026 年 9 月），可能随平台迭代失效。
3. **地理特殊性**：收货地址位于中国西北偏远地区，运费与配送可达性成为决定性变量，这一条件在一般研究中被忽略。
4. **单一语言与生态**：结论仅适用于中文电商生态，向其他语言圈电商的外推需谨慎。

## 8 结论与未来工作

本文报告了一套面向真实中文电商平台的浏览器级购物智能体方法，并在七个平台上完成了系统性实测。主要结论是：**在强风控环境中，智能体的瓶颈不在模型推理，而在（a）浏览器载体的真实性，（b）状态判据的可靠性，（c）人机边界的清晰划定。**

我们认为，本文最有价值的部分不是任何单一技术，而是那一组**反直觉的失效记录**：UA 伪装对两个平台的反向效应、接口"成功"却静默失效、减号与加号共用类名、以及"观测行为触发风控升级"。这些教训无法从沙箱基准中获得，只能从真实平台的碰撞中获得 —— 这与 Xue 等人[^6] 关于"进步幻觉"的判断在此得到了工程侧的印证。

**未来工作**包括：①将本方法的多平台适配抽象为可组合的领域层，降低新平台的接入成本；②引入视觉语言模型作为 DOM 感知失效时的感知回退通道；③构建**中文电商环境下的真实在线基准**，填补现有基准在地域与生态上的空白；④研究"人机交接"的交互协议，使智能体在触及边界时的移交更自然、更安全。
