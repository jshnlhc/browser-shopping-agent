# 电商自动比价与加购

## Overview

在中文电商平台代替人完成「搜索 → 进详情 → 比价 → 加购 → 改数量 → 核价 → 把付款界面交给用户」。核心原理：**用有头 Edge + CDP 操作真实浏览器**，把登录态、反爬、懒加载都交给真实浏览器解决，只在必要时才退回到解析 DOM 或接口。

**下单动作永远留给用户**：可以加购、改数量、进结算页核对运费与实付、把窗口显示出来并把付款界面停在用户面前，但**绝不点击「立即支付」**。

## When to Use

- 用户要买某商品、要比价、要「帮我加入购物车」
- 要确认「到底要付多少钱」（含运费、优惠、到手价与实付的差异）
- 页面显示「加载中」、商品列表为空、搜索无结果
- 接口返回成功但页面没变化
- 要求「不要弹浏览器窗口」，或反过来要求「把付款界面调出来」

不适用：得物（网页端只有 App 下载引导）、抖音商城 PC 端（强制 `type=general`，无商品搜索）、苏宁（部分品类无货）。别在这三家身上耗时间。

## 环境

| 项 | 值 |
|---|---|
| 独立 profile | 你自己的专用目录（例如 `~/.browser-profiles/shopping`） |
| CDP 端口 | 9335，**有头模式** |
| 启动 | `msedge.exe --remote-debugging-port=9335 --user-data-dir=<profile> --disable-blink-features=AutomationControlled` |
| 隐藏窗口 | user32 `ShowWindow(hwnd, 0)`（SW_HIDE）——有头的能力、无头的体验 |
| **恢复窗口** | user32 `ShowWindow(hwnd, 9)`（SW_RESTORE）+ `ShowWindow(hwnd, 5)` + `SetForegroundWindow(hwnd)`；用 `IsWindowVisible(hwnd)` 验证 |
| 已登录 | 京东、淘宝/天猫、拼多多、闲鱼、抖音 |

取窗口句柄：`Get-Process msedge | Where-Object { $_.MainWindowHandle -ne 0 }`。**浏览器被隐藏时句柄依然存在、进程数不会归零——窗口「看不见」不等于进程死了**，先探 CDP 9335 再判断，不要急着重启浏览器（重启可能丢标签页与结算快照）。

## 登录判据

**cookie 存在 ≠ 登录有效。** 京东掉线时 cookie 里仍有 `pin`+`thor`，cookie 脚本照样报「已登录」，但业务页全 302 到 `passport.jd.com`。唯一硬判据 = 打开受保护页面，看是否被重定向到登录页。

**UA 是雷区，且对两平台反向。** 淘宝搜索页商品一直「加载中」的根因是 HeadlessChrome UA，覆盖成正常 Edge UA 后文本从 838 字符恢复到 7672；但京东把凭证绑设备指纹，**改 UA 会踢掉整个京东登录态且切回有头也救不回**，只能让用户重新扫码。两者不能在同一 profile 上兼顾。

## 价格的正确读法（最容易误判的部分）

1. **「到手价」是预估价，不是结算价。** 京东官方定义：`预估到手价 = 标价 − 优惠券 − 满减 − 新客优惠…`，并明确写出「**购买多件商品而满减活动仅支持享受 1 次**」。实测两件膜标签价相加 ¥20.60，合并结算实付 ¥27.10，差 ¥6.50 就是这条规则造成的。
2. **所以「分开下单更省」往往是错的** —— 分单后满减照样只享 1 次，还要多担一次运费。要下这个结论必须按结算页逐单实测，不能拿标签价相加去推。
3. **结算页（`trade.jd.com/shopping/order/getOrderInfo.action`）是唯一权威价格来源**，它给出每件分摊后的实付、商品总额、共减金额。
4. **运费判据**：自营基础运费 6 元，订单实付**满 59 元免基础运费**（PLUS 有无限免邮）。判断本单有没有运费，**不要靠规则推断，直接扫结算页有没有「运费」金额行**：若全页只出现页脚「配送费收取标准」这个帮助链接、没有金额行 ⇒ 本单免运费。
5. 结算页可能同时出现两个「共减」口径（商品优惠与支付优惠），别把它们相加；以「商品总额 − 共减 = 实付」这一行为准。

## 支付前置校验（实名墙）——必须交给用户

访问结算页可能被**强制重定向**到 `authpay.jd.com/auth/toAuthPage.action`（标题「安全中心」）→ 京东金融实名认证页，要求填**银行卡号 + 该卡在银行预留的手机号 + 短信验证码**。这是支付前置条件，不是可选营销弹窗。

- **触发因素**（实测）：短时间内反复打开结算页；或在结算页把「完善实名信息」引导弹窗点掉「下次再说」。为核对运费而连续抓结算页，很容易把风控级别顶上去。
- **正确做法**：核对运费/实付**一次到位**（一次抓取就把运费、商品总额、共减、实付全读到），不要反复导航结算页。
- **遇到实名墙时**：停手，把页面留在原地或退回购物车，交给用户本人操作。**绝不代填、绝不索取短信验证码**。购物车与登录态不会因此丢失（实测重定向后购物车仍是原样的合计与件数）。
- 同类前置校验还有：支付密码、手机验证、白条协议签署——凡涉及银行卡/短信/密码的步骤一律转交用户。
- 风控通常有时效性，隔一段时间再试可能自动放行；但**不要在风控期内反复戳**，那只会加重校验。

## 抓取

- 对抗懒加载：`Emulation.setDeviceMetricsOverride` 把视口放大到 1512×2600，再反复 `window.scrollTo(0, document.body.scrollHeight)`。
- 京东搜索页会限流（「抱歉由于访问频繁导致无法搜索」）→ 放慢节奏，优先抓商品详情页。
- **拼多多是硬骨头**：页面零 `<a>`、HTML 里没有 `goods_id`、XHR 响应体被加密成 `{"rc-res-data":"..."}`。唯一突破口 = CDP `Input.dispatchMouseEvent` 在商品位置**真实坐标点击**，再读落地 URL 拿 `goods.html?goods_id=...`。
- 链接藏在哪：京东在 `chat.jd.com/index.action?...pid={SKU}`；淘宝/天猫是 `detail.tmall.com/item.htm?id=&skuId=` 与 `item.taobao.com/item.htm?id=`。

## 购物车

| 动作 | 通道 | 有效性 |
|---|---|---|
| 加购 | `cart.jd.com/gate.action?pid={sku}&pcount={n}&ptype=1` | ✅ |
| 改数量 | `cart.jd.com/changeNum.action?pid=&pcount=` | ❌ 返回 `{"isLogin":1,...}` 像成功，新版 SPA 根本不理会 |
| 改数量 | 点击减号按钮 | ✅ |

新版购物车要点：

1. 类名是 CSS Modules 哈希（`_flex-plus-container_1ep1a_41`），**减号与加号用的是同一个类名**，搜 `minus` 永远搜不到。识别方法看内部图标：只有 `_flex-plus-horizontal`（一条横线）= **减号**；横线+竖线 = 加号。数量为 1 时减号带 `_is-disabled_1ep1a_62`。
2. 点击要派发完整序列 `pointerdown → mousedown → pointerup → mouseup → click`，然后等 3–4 秒。
3. **购物车的「合计/商品总额」只统计已勾选的商品** → 判断数量到底改没改，要看**商品总额**（原价 × 件数）：`¥39.40 → ¥19.70`（正好减半）才证明减号真的生效。
4. 勾选框分三级：全选 / 店铺级 / 商品级。按上下文定位，**不要误勾用户自己加的商品**。
5. **必须新开页面复核**服务器端状态，页面内的数字可能是没刷新的快照。
6. 页面加载比想象中慢（14 秒时可能只渲染出搜索框）→ 要轮询等待元素出现。

## 选品约束

- **超声波指纹屏（荣耀 WIN、Redmi K80 Pro 等）选膜的决定性因素是「厂商标注 + 膜厚」，不是「全胶/边胶」这个分类。**
  - 厚度：业界对超声波机型的建议是 **0.15–0.2mm**；到 0.25mm 就有影响解锁的风险。准确厚度要去**品牌官网产品页**拿（商品详情页"规格参数"通常只写「工艺：电镀 全胶」，不写厚度）。
  - 认证：**优先选标题/规格里明确写「超声波秒解锁」「指纹秒解」的型号**，这是厂商针对超声波机型的适配声明，比工艺分类可靠得多。
  - 官方立场：vivo、荣耀官方支持页都明确说第三方膜的**材质和厚度**会影响超声波发射与反射；荣耀给出的解法是「贴完后删除全部指纹并重新录入」，并建议打开「触控灵敏度」。
- **贴膜操作清单（交付给用户）**：①贴之前先录一遍指纹；②贴完删掉全部指纹重新录入；③打开 设置→显示（或 无障碍→交互和操作）里的「触控灵敏度」；④录入时把指腹侧面、指尖各部位都多录几遍；⑤当场测试解锁，不灵就走 7 天无理由退。
- **售后判据**：京东自营标「7天无理由退货」；「7天价保」**不覆盖限时立减/消费券/国家补贴等产生的降价**，别把价保当成必然兜底。
- **新疆/偏远地区运费是决定性成本变量**：拼多多某款膜要另加 28 元运费；优先京东自营（配送与售后最稳）。
- 京东自营钢化膜常见规格就是 **2 片装，通常没有单片**：用户说「一片」时最小购买单位仍是 1 件。
- 省钱路径：京东更低价的通道是京喜自营/百亿补贴（白牌工厂补贴），但**小件商品不值得为此折腾**，别为了几块钱把配送与售后换成不确定。

## 硬判据（最常出错的地方）

| 看到的现象 | 不要下这个结论 | 正确判据 |
|---|---|---|
| cookie 里有 `pin`/`thor` | 登录正常 | 打开业务页看是否 302 到登录页 |
| 接口返回 `{"isLogin":1}` | 改数量成功 | 重开购物车看商品总额 |
| 商品行标着「到手价 ¥X」 | 结算就是这个价 | 到手价是预估价；以结算页分摊实付为准 |
| 两件标签价相加 ≠ 合计 | 算错了/有隐藏费用 | 满减每单只享 1 次，差额通常来自这里 |
| 订单不满 59 元 | 一定收 6 元运费 | 扫结算页有无「运费」金额行，没有就是免了 |
| 浏览器窗口看不见 | 浏览器挂了 | 先探 CDP 9335；句柄通常还在，`ShowWindow(h,9)` 即可恢复 |
| 类名里搜不到 minus | 没有减号按钮 | 看内部图标结构 |
| 到手价没变 | 数量没改成 | 看商品总额（原价 × 件数） |

## 开源项目的参考与红线（2026-09 实测评估）

这个领域**没有"写一次永久可用"的脚本，只有"能看见、能重抓"的方法论**。评估过的两类项目：

- **`frieren-123/shopping-agent-ai`**（LLM 跨平台比价，京东/淘宝/唯品会）：可借鉴 `analysis/scorer.py` 的智能打分（价格×销量×店铺信誉加权）、`llm_analyzer.py` 的参数提取与去营销话术、报告生成、用户画像。**但它的路线不可照搬**：走无头 Playwright（实测会被淘宝判定「加载中」、被京东踢掉登录态），京东部分要靠 Crawl4AI + PaddleOCR 视觉识别——这正是无头方案的天花板。**它还把作者本人的 2MB 淘宝 cookie 提交进了公开仓库**，是凭证管理反面教材。
- **`hamibot/hamibot`**（安卓 JS 自动化，★3116）：**无需 root**，基于无障碍服务（`com.stardust.automator` 封装 UI 树 + BFS/DFS 选择器）。技术上是手机端最现实的路径，但①无障碍服务是电商 App 的重点风控特征；②其脚本市场几乎全是刷金币/养号/刷单，与平台规则高度冲突。**结论：能点，但不该用**。

**三条硬红线**：

1. **凭证绝不落盘、绝不提交**：登录一律在用户自己的浏览器里完成（独立 profile 是加密存储）；永远不要把 cookie/token 写成项目文件，也不接受任何要求你粘贴密码或 cookie 的第三方程序。
2. **不用无头浏览器做电商**：无头特征会导致淘宝「加载中」、京东掉登录。有头 + CDP 是唯一同时满足两家的路线。
3. **凡涉及银行卡/短信/密码/人脸的前置校验，一律停手交给用户**。
